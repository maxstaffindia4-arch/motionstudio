# Phase 0 Spike Report — Transparent Export on Linux/Docker

**Date:** 2026-11-17 · **Scope:** prove the Motion Lab transparent-export method
works end-to-end on compositions produced by `@motion-studio/engine`, inside a
Linux/Docker render pipeline.

## Verdict: **CONDITIONAL GO**

The **method is verified**: native `hyperframes render --format mov`
(ProRes 4444 / `yuva444p12le`) + ffmpeg-derived VP9-alpha WebM and
composited MP4s produces correct transparent output from engine scenes —
**84/84 automated checks pass**, including the glow-box regression test on
both the MOV master and the derived WebM.

The **Docker image itself is untested**: no Docker daemon exists on the
spike machine, so `Dockerfile` is provided but not built. One
`docker build && docker run` smoke test is required before Phase 5
(see "Remaining risks"). The render scripts are platform-agnostic and ran
unchanged on Windows; nothing in them is Windows-specific.

## Method (ported verbatim from Motion Lab `src/server/hyperframes.ts`)

| Stage | Command |
|---|---|
| Master | `hyperframes render <dir> -o <name>.mov --format mov --fps 30` (cwd = composition dir) |
| WebM | `ffmpeg -i master.mov -c:v libvpx-vp9 -pix_fmt yuva420p -crf 24 -b:v 0 -auto-alt-ref 0 -row-mt 1 -an out.webm` |
| MP4 chroma | `ffmpeg -f lavfi -i color=c=0x00FF00:s=<W>x<H>:r=<fps> -i master.mov -filter_complex "[0:v][1:v]overlay=shortest=1,format=yuv420p" -c:v libx264 -crf 18 -preset medium -pix_fmt yuv420p -an out-chroma.mp4` |
| MP4 opaque | same, `color=c=0x0B0F19` → `out-full.mp4` |

One deliberate, documented deviation: Motion Lab hardcodes `s=1920x1080`
in the lavfi colour source. The spike parameterizes it per fixture canvas
(required for vertical/square/custom); the filter graph and codec args are
identical.

Native `--format webm` was **not** used (Motion Lab verified it emits
`yuv420p` with no alpha).

## Fixtures

16 compositions generated by `scripts/gen-fixtures.ts` from engine scenes:

- `text-slam`, `number-counter`, `glow-sweep` × {landscape 1920×1080,
  vertical 1080×1920, square 1080×1080, custom 1280×720}, all
  `output: transparent`, 5 s @ 30 fps.
- `glow-torture` × same 4 canvases: text-shadow glow (blur 90) plus four
  box-shadow glow cards (blur 20/45/70/120 px @1080) — the Motion Lab
  "box artifact" regression fixture. Required a small engine addition:
  `StackStyle.glow` → `box-shadow` (committed separately, `05433f7`).

## Results — `scripts/verify.ts` (84/84 PASS)

Checks per fixture: ffprobe pixel format, alpha==0 pixels composite to
exactly red/black/white/green backdrops, glow-box analysis (alpha≈0 in the
ring outside content, no straight low-alpha edges ≥30 px, glow skirt
extends ≥6 px past the solid core per connected component), counter
frames at 1 s/2 s/3 s.

| Check | MOV master | Derived WebM |
|---|---|---|
| pix_fmt / alpha signal | `yuva444p12le` prores — all 16 PASS | `alpha_mode=1` VP9 tag — all 16 PASS |
| transparent pixels = backdrop exactly | 16/16 PASS (~9k–39k samples each) | 16/16 PASS |
| glow-box (no rectangular edge / clipped halo) | 8/8 PASS (glow-sweep + torture) | 8/8 PASS |
| counter values differ @1s/2s/3s | 4/4 PASS (distinct md5 per frame) | n/a (checked on master) |

**No stage introduced a glow box.** The derived WebM's alpha matches the
MOV master's behaviour on every glow fixture.

## Timing & size (Windows host, hyperframes 0.9.59, ffmpeg Lavc60)

Per fixture ≈ **35–115 s MOV render** + **10–95 s WebM encode** +
**1.5–20 s per MP4**. Outliers: `number-counter` MOV renders took
300–345 s twice (unexplained; possibly Chrome/font-cache contention —
worth watching in Docker). MOV masters are large: **11–213 MB** each,
**~1.1 GB total** for 16 fixtures (ProRes 4444 12-bit is heavy — fine for
an intermediate, not a deliverable). WebM outputs are tiny (0.07–0.6 MB)
because scenes are mostly transparent; MP4s 0.05–0.2 MB.

## Problems found & fixes (in spike scripts, not by weakening checks)

1. **ffprobe reports WebM `pix_fmt=yuv420p` even with alpha.** VP9 alpha is
   signalled by the `alpha_mode=1` container tag, not the pix_fmt — the
   verify script checks the tag (matches Motion Lab README).
2. **This ffmpeg build's native `vp9` decoder drops the alpha
   side-channel.** `ffmpeg -i x.webm -pix_fmt rgba` returns alpha=255
   everywhere; `alphaextract` fails. Forcing `-c:v libvpx-vp9` before `-i`
   decodes alpha correctly. `verify.ts` does this automatically for `.webm`
   inputs. **Action for Phase 5:** any WebM alpha consumer must use the
   libvpx-vp9 decoder (or verify the Docker image's ffmpeg behaves the same
   — Debian's ffmpeg may differ; the check will catch it).
3. **hyperframes requires ffmpeg+ffprobe on PATH itself** (it shells out
   for MOV muxing). `render-all.ts` prepends the ffmpeg dir to PATH for
   the child process.
4. **First-render font fetch needs network.** Hyperframes pulled
   Inter/Montserrat from Google Fonts at render time and cached them under
   `$HOME/.cache/hyperframes/fonts`. The Dockerfile warms this cache at
   **build** time so renders need no network.

## Dockerfile

`spikes/render/Dockerfile`: `node:22-bookworm-slim` + ffmpeg (apt) +
Chromium shared-library deps + `hyperframes@0.9.59` (npm -g) + tsx;
non-root `app` user; fixtures/scripts COPY'd in; font cache warmed at
build; default CMD runs render-all + verify into a mounted `out/`.
**Image size: not measured (no Docker on spike host).** Estimate
~1.5–2.5 GB (Chromium deps + npm global + fonts cache).

Build/run:

```sh
docker build -f spikes/render/Dockerfile -t motion-studio-render .
docker run --rm -v "$PWD/spikes/render/out:/work/out" motion-studio-render
```

## Remaining risks for Phase 5

- **Docker smoke test outstanding** — Chrome sandboxing inside the
  container (may need `--no-sandbox` or `SYS_ADMIN`; hyperframes manages
  its own browser, watch for missing libs on first run).
- Debian ffmpeg's VP9-alpha decode path may differ from this Windows
  build — `verify.ts` will flag it immediately.
- MOV masters are ~40–210 MB per 5 s clip; Phase 5 workers should stream
  derive→delete or use shorter durations / lower ProRes profile if disk
  matters.
- `number-counter` render-time outliers (300 s+) need a second look —
  possibly first-run font/browser cache; re-measure inside Docker.
